These steps are for the agent/operator, not commands for the user to copy.
Production application and bank access require their respective user approvals.

1. Keep the feature disabled. Recheck `supabase/pending-preflight.sql` against the
   selected Transactions project. Expected: PostgreSQL 17.6, privileged migration
   role, existing account deletion function, and no pending schema/table/RPC.
   Stop on a mismatch and inspect metadata; never replace existing pending data.
2. Apply only `supabase/migrations/20261026211104_pending_card_snapshots.sql`
   through the migration tool. It is additive and transactional, with bounded
   lock/statement timeouts. Do not run `validation/pending-db/bootstrap.sql` on

   Set `VITE_PENDING_APPROVALS=true` as a **build-time** setting and rebuild. Keep
   `render.yaml` consistent with that chosen release setting. Changing only the
   runtime environment cannot update an already compiled Vite bundle.
4. Check the signed-in panel reads snapshots and handles an empty table without
   initiating bank access. Refreshing this panel only reads saved observations.
   The separate “refresh from banks” action still initiates a bank sync.
5. Prepare the local bank-sync installation from this candidate under supported
   Node (22.22.2+; validation used 24.19.0). Preserve existing credentials/config.

6. Only after explicit permission to contact the issuer: perform pending binding

   Posted totals and exports must remain unchanged by pending rows. A stale or
   failed observation must keep its warning. Approvals may have changed since

## Rollback

Rebuild with `VITE_PENDING_APPROVALS=false` and disable pending collection locally
through the existing explicit binding flow. Stop bank runs if cleanup is uncertain.
Keep the additive table and its data; do not drop tables, clear snapshots or
rewrite posted history as a rollback. Existing posted-only behavior remains
available with pending collection disabled.

## Repeatable isolated validation

`validation/pending-db/verify.mjs` rejects non-loopback endpoints and database
names outside `pinkas_isolated` / `pinkas_isolated_<suffix>`. It uses synthetic
UUIDs and a synthetic JWT signing key. `--prepare` creates the fixture, applies
the migration and verifies the deletion function stayed unchanged; `--prepared`
runs the real HTTP/SQL cases after PostgREST starts. Use a fresh disposable DB
for each run. The complete service configuration is in the `pending-database`
job of `.github/workflows/ci.yml`. No `.env`, Keychain or bank service is needed.
